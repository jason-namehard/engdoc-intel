# engdoc-intel · 工程报告智能抽取与检索服务

> 作者：（[jason-namehard](https://github.com/jason-namehard)）。状态：开发中。
> 开发过程使用 AI 编程 Agent 协作（规划、审查、编码分工），每个模块由作者本人运行验证并记录评估结果。

## 要解决的问题

工程单位手里有大量技术报告（PDF / Word / 扫描件），关键数值散落在正文和表格里，现在靠人工翻找、摘抄、复核。
本项目提供一个服务，做四件事：
1. 解析和清洗报告；
2. 按问题检索原文；
3. 把关键字段抽成结构化 JSON 并校验；
4. 由 Agent 调用确定性计算块做复核。

数据集是水库防洪安全复核报告和《山东省小型水库洪水核算办法》；方法本身面向通用工程技术文档。

## 模块与验收

每个模块单独开发、单独验收。上一个模块关卡没通过，不开下一个。

| 模块 | 内容 | 验收 |
|---|---|---|
| M1 解析清洗 | DOCX / 文本 PDF / 扫描 PDF（OCR 可后置）→ 统一文档记录（正文段落、表格、页码、章节、来源）；单位统一，缺失和冲突标记 | 全部样例报告可解析；输出 JSONL；解析覆盖率报告；单元测试 |
| M2 检索 | 固定块与父子块切分；BM25（SQLite FTS5）、向量（bge-small-zh）、RRF 混合，可选重排 | ≥30 题人工审核评估集；Recall@5、MRR 对比表；每种方案的失败样例 |
| M3 结构化抽取 | 字段用 pydantic 定义；规则、提示词 + LLM、LoRA 三种方法对比；JSON 校验与失败重试 | 训练集和测试集按报告划分、不泄漏；字段级准确率；端到端成功率（解析失败算错）；说清各方法的胜负原因 |
| M4 服务化 | FastAPI：`/ingest`（异步任务）、`/jobs/{id}`、`/search`、`/extract`；SQLite 任务表做队列；并发上限、超时、重试、熔断；结构化日志；中断后能续跑 | 接口测试；并发压测脚本与结果；人为杀进程后任务能恢复 |
| M5 Agent 层 | 真实 LLM 的工具调用循环（OpenAI 兼容接口，可接 Ollama 或本机网关）；工具包括检索、抽取、Engi-Block 计算块；最大步数、无进展检测、写操作需人工确认；用 MCP 对外提供工具 | 10 个任务的 Agent 评估（成功率、步数、工具错误率）；完整调用日志 |
| M6 交付 | Dockerfile / docker compose；README 的架构图；评估报告；3 分钟演示视频 | 一台干净机器按 README 能跑起来 |

## 前期实验（本项目在其基础上重写）

| 实验 | 结论 | 用于 |
|---|---|---|
| RAG 对照：固定 / 父子切块 × BM25（FTS5）/ bge-small-zh / RRF，30 题评估集 | 父子切块 + BM25：Recall@5 = 1.00、MRR = 0.928；该语料上切块策略的影响大于检索器 | M2 |
| 抽取对照：Qwen2.5-0.5B + LoRA（r=8）vs 提示词 + 规则 | 字段准确率 0.352 vs 0.958；格式固定的报告规则更优，小模型容量和数据量不足 | M3 |
| LangGraph 复刻多角色审查流程（模拟节点，无真实 LLM 调用） | 验证了条件分支和同进程中断恢复 | M5 |
| Engi-Block：带单位、适用范围、规范出处和验收算例的确定性计算块 | 21 个水文 / 堰流计算块，以及求根、插值组合子 | M5 |
